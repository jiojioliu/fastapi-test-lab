01 / FUNCTIONAL TESTING

先用 Postman 跑通完整业务链

从登录、商品查询到创建订单，确认接口契约、鉴权与响应断言都符合预期。

前置条件服务已启动 账号admin / admin123 产出无失败断言
01

导入集合并确认环境

下载集合后导入 Postman，检查集合变量 baseUrl 是否为本地服务地址。

下载集合
02

执行登录并保存 Token

运行“Login and capture JWT”。成功后集合变量会自动保存 `access_token`。

POST /api/auth/login
03

用 Collection Runner 验证业务链

按 Authentication → Catalog → Orders 的顺序执行，确认订单创建返回 `201`。

预期结果

所有请求通过测试断言，订单响应包含订单编号、金额和支付方式。

02 / PERFORMANCE TESTING

先做基线，再逐步增加并发

使用随附 JMX 计划验证登录、商品查询、慢响应和订单创建在并发下的稳定性。

15 min预计用时
默认负载8 线程 × 10 次 首轮建议1 线程 × 1 次 产出P95 与错误率
01

导入测试计划

打开 `.jmx` 文件，确认 HTTP Request Defaults 中的主机和端口与本机服务一致。

下载计划
02

先运行一轮冒烟基线

将线程数设为 1、循环次数设为 1，确认每个断言全部通过，再调整负载。

Threads 1 · Ramp-up 1s · Loop 1
03

加压并对照实时图表

切回运行概览，观察 P95 延迟、错误率与请求曲线。异常时优先查看断言失败样本。

预期结果

基线无异常 5xx；加压后能明确说明吞吐量、P95 延迟和首个性能瓶颈。

03 / PROXY INSPECTION

在代理历史中定位一次真实请求

通过 Burp 观察浏览器发出的登录与订单请求，再到 Repeater 中安全地修改和重放。

10 min预计用时
监听地址127.0.0.1:8080 目标HTTP 明文流量 产出可重放请求
01

确认代理监听已开启

在 Proxy → Proxy settings 中启用 listener，并用 Burp 内置浏览器访问本站。

127.0.0.1:8080
02

筛选本地请求

在 HTTP history 中按 Host 过滤，登录后找到 `/api/auth/login` 与 `/api/orders`。

Host contains 127.0.0.1
03

发送到 Repeater 并观察响应

确认 Authorization、Idempotency-Key 和 JSON Body，再修改支付方式或商品数量验证校验逻辑。

预期结果

能够从代理历史定位请求，并在 Repeater 中解释状态码、响应头和业务校验结果。

04 / PACKET OBSERVATION

用协议视角验证一次请求往返

捕获本地回环流量，从 HTTP 请求行、响应头与 JSON Body 对照应用层日志。

12 min预计用时
接口Npcap Loopback 端口8000 产出请求 ID 对照
01

选择回环接口并开始捕获

Windows 通常需要 Npcap；选择 Adapter for loopback traffic capture 后开始抓包。

02

生成一条特征明确的请求

在应用内执行请求回显，随后在 Wireshark 应用显示过滤器。

tcp.port == 8000 && http
03

核对请求与响应

展开 HTTP 流，对比路径、状态码、`X-Request-ID` 与响应 JSON，说明传输层和业务层的关系。

预期结果

能定位完整 HTTP 往返，并用 Request ID 将抓包结果与页面请求日志对应。
